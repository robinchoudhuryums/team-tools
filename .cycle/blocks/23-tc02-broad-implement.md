Findings implemented:
- TC-02 — a rep's break adjustment (Apply now, or an approved request) rewrote the LAST Lunch Out / Lunch Return of that day (findExistingPunch_ / buildAdjustPunchIndex_), so on a multi-break day a forgotten second break overwrote the first, and a correction of the first break moved the second. The request carried no intent, so neither the server nor the approving manager could tell "add a missing break" from "correct the one I have". Implemented as the operator's option (a): an intent control, carried on the request, re-checked at approval; the manager range path gets the same treatment (refuse the ambiguous day).

REGRESSION RISKS:
- A break request filed BEFORE this deploy carries no intent; on a day that already has that punch its approval is now REFUSED (the row stays Pending, the error says why and the queue row says so in advance). The manager denies it and the rep files again. Intended — guessing was the defect — but it is visible friction on the first day.
- A rep cannot file a break adjustment while that day's breaks are loading or after the read failed (the modal says so). Fail-closed by design; Clock In / Clock Out are unaffected.
- Range mode now refuses a range that includes a multi-break day when the break slots are filled (it used to rewrite the last break). Leaving the break slots blank, or Day Edit per day, is the way through; the error names the days.
- `writeAdjustPunchForEmployee_` now RETURNS `{error}` for a refused break; every caller checks it (approval, range, repair); the resume path writes a ClockOut, which never refuses.

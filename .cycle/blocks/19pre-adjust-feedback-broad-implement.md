# 2026-08-31 #2 — Punch-adjustment feedback loop (operator: approved same-day adjustment left the rep still seeing "Clock In")

---BROAD SCAN IMPLEMENTATION SUMMARY---
Findings implemented:
- ADJ-1 | The Clock view never re-asked the server. An approved same-day adjustment IS correct server-side (an `ADJ-ClockIn` row is a real punch — `normalizeType_` strips the prefix, `getTodayPunches_` includes it, `getNextActions_` returns Lunch Out / Clock Out), but `clkRefreshState_` fired only on view-enter, focus/visibilitychange and day rollover, so an agent sitting on a focused Dashboard kept pre-approval buttons indefinitely. The refresh function's own comment already named this case — the machinery existed, the TRIGGER did not.
- ADJ-2 | A pending request was invisible where it mattered. It rendered ONLY inside the Adjust modal (`#adj-pending-list`); close the modal and the Clock view showed no trace, so the rep saw a bare "Clock In" and the natural move was to punch again "to be safe". (Not destructive — `writeAdjustPunchForEmployee_` UPDATES the existing row on approval — but nobody was told that.)
- ADJ-3 | Neither approval NOR denial notified the rep. `updatePunchAdjustStatus` wrote the punch, wrote an audit row, and returned. Punch adjustments were the ONLY request type with no notification (time off has always had `notifyEmployeeOfDecision_`; coaching / EmpDocs / training assignment all notify), and a denial was indistinguishable from an approval that had not propagated.

CHANGES:
ADJ-1 | tc/script_clock.html | `clkPeriodicReconcile_` — throttled `CLK_RECONCILE_MS` (3 min) reconcile riding the EXISTING 1Hz clock tick rather than a second interval (INV-190's cost rule), gated on `currentView === 'clock' && !document.hidden` so nothing polls from Call Notes, a background tab, or another tool's pop-out. `clkRefreshState_` stamps the window BEFORE its RPC, so every trigger (enter, focus, rollover, periodic) postpones the next periodic call and the 1Hz tick can never queue a second fetch while one is in flight — without that stamp the first tick fired a duplicate one second after the view-enter refresh. Deliberately NOT a shell-wide poll: the reminders ticker already refreshes state inside the end-of-shift window, and making it unconditional would put a per-minute RPC on every rep for state only the Clock view renders. The same call also catches a manager Day Edit, a past-day approval, and a self-undo made in another window.
ADJ-2 | Code.js + tc/script_clock.html | `empPendingAdjustments_(empId, dateIso)` — today's PENDING requests, RANGE-bounded (the `empIsOffToday_` precedent, never `getDataRange`), READ-ONLY and never provisioning the tab (`getEmployeeState` is the app's hottest endpoint; a deployment with no requests yet must not have it create a sheet), status normalized at the ONE read (the TO/DR.STATUS family — a padded `" Pending "` cell still counts), failing toward `[]` which is exactly the pre-fix behaviour. Shipped additively as `pendingAdjustments` and rendered by `clkPendingAdjustHtml_` as an info-toned `role="status"` chip ABOVE the punch buttons — the position is the point, since it is what the rep sees at the moment they would otherwise re-punch. Empty list or absent field renders NOTHING, so an older server is byte-identical.
ADJ-3 | Code.js | `notifyEmployeeOfAdjustDecision_` on BOTH outcomes, wired through the `notifyAfter` closure so the send fires AFTER `lock.releaseLock()` (M-7 — a MailApp send inside the one project lock stalls every rep's punch). Branded via `buildBrandedEmailHtml_` with `esc_`'d fields (INV-105), plain-text fallback, green/red by decision, `safeWebAppUrl_('clock')` CTA, best-effort try/catch (INV-14 — the approval is already committed). The denial copy says the timesheet is UNCHANGED, which is the whole reason a denial needs its own message.

UMS Team Tools  ·  Design handoff  ·  Intake emails

Built for transcription

The receiving team reads these field-by-field and types each value into the CRM. That single fact settles most of the design: field order stays exactly as filled, nothing is summarised, nothing is hidden, and no section gets promoted. Your two "keep the order" answers were the right call — reordering would have broken the one workflow these emails serve.

What changes is everything that makes a value hard to read off and retype: the label currently outweighs the value, identifiers are set in proportional type where a transposed digit is invisible, a 40-word attestation breaks the column rhythm mid-form, and an empty cell can't be told from a not-applicable one.

01 — The reframe

A source document, not a briefing

I came in assuming the recipient was deciding something. They aren't — they're copying. Worth recording what that ruled out, because the instincts it kills are the ones a redesign reaches for first.

Ruled out
An action summary at the top; promoting scheduling/permission; recommendation-before-questionnaire; hiding empty rows. Every one of these makes the transcriber hunt for a field that used to be where they expected it.
What matters instead
Never losing your place mid-column. Reading a member ID without transposing a digit. Knowing whether a blank means "leave it empty" or "go chase it". Getting a value cleanly onto the clipboard.
Scope
PMD → Sales, PAP → Sleep, PPD → Sales. PMD and PAP share intakeEmailShell_ and have never had a design pass; PPD's got one, but predates the questionnaire treatment below.
The four defects, all transcription defects
  • The label outweighs the value. Labels are bold navy; values are plain grey-black. When you're reading to retype, the value is the payload and the label is the index — the emphasis is backwards.
  • Identifiers are proportional. SSN, member IDs, DOB, phone and fax all set in Arial, where 1/7 and 0/O are hard to separate and a doubled digit is invisible. These are the exact fields where an error is expensive and silent.
  • Attestations break the column. PMD index 24 is a 40-word sentence in the label cell with a one-word answer beside it. Mid-form, it stops the eye and pushes the value column off its rhythm.
  • Three kinds of blank look identical. SSN is a fallback for missing insurance; discharge date is conditional on being in a facility; sleep-study details depend on the prior answer. Not-applicable, not-asked and missing-but-needed all render the same.
02 — The three emails

Same fields, same order, readable off the screen

Section headers and field sequence are exactly the live banks. Values now lead, identifiers are monospaced, attestations run full-width, and the label column is a fixed width so the value column starts at the same x on every row in the email.

03 — The rules

Four changes, applied to all three

1 · The value leads
Label 12px #737c8c regular; value 13.5px #0f1623 bold. Label column pinned at width="46%" on the first row of each table, so the value column starts at the same x on every row and the eye can run straight down it. Tuned against the longest verbatim bank labels, EN and ES — several wrap to two lines, which is fine: both cells are vertical-align:top, so a wrapped label never moves its value. Zebra #ffffff / #f8fafc with a 1px #eef0f4 rule — losing your line mid-transcription is the failure this prevents.
2 · Identifiers are monospaced
'Courier New', Courier, monospace — the one mono stack safe across Outlook, Gmail and Apple Mail. Applied to phone, fax, DOB, SSN, member IDs, height, weight, and the HCPCS codes. Fixed advance width makes a transposed or doubled digit visible; letter-spacing:.03em (.06em on IDs) separates runs. Insurance carrier stays proportional and the ID drops to its own line beneath — they're pasted into different CRM fields.
3 · Attestations run full-width
The condition is a checkbox index whose bank label is a declarative sentence rather than a question — today exactly PMD 24 and PAP 26. They become a colspan="2" row: green check, Confirmed by agent, then the sentence at 12px. Nothing to transcribe, so it stays out of the value column entirely. The rest of the checkboxes list (PMD 22/25, PAP 24) are ordinary questions and keep their Yes/No in the value column — including permission-to-schedule, whose answer Sales needs. A false value renders the same row in #8a4500 with Not confirmed — it must never simply vanish.
4 · Two kinds of blank
You skipped this one, so: distinguish them, minimally. — not provided means the field was asked and left empty; the transcriber leaves the CRM field empty. Not applicable — reason means a prior answer made it moot ("patient at home", "no prior eval", "insurance on file"), and the reason comes from the governing answer, not a guess. Both in 12px #a5acb8, visibly lighter than real values so they never read as data.
One thing worth a look — you have this already, on the wrong side
On a successful intake send the app already builds a CRM-paste note template and copies it to the clipboard — for the sender, who has just finished with the patient and isn't the one entering it. The person doing the CRM entry is the recipient, and they get a form to retype by hand. If the template is close to what they paste, putting the same block at the foot of the email (or attaching it as .txt) removes the transcription step this whole redesign is otherwise just making faster. I haven't designed it — it depends on how well your CRM takes a paste, which you'd know. Worth ten minutes of your time to check.
Do not break these
  • Field order and section headers are the bank. Nothing here reorders, merges or drops a field. The layout constants (INTAKE_PMD_LAYOUT / INTAKE_PAP_LAYOUT, server-authoritative) are unchanged — this is presentation only.
  • The client/server layout coupling stays pinned. INTAKE_PMD_CLIENT / INTAKE_PAP_CLIENT must keep mirroring the server, and test_intake_layoutCoupling must keep passing. Do not drive the attestation styling off the whole checkboxes list — it holds ordinary Yes/No questions too, and treating them as attestations would drop their answers. Key off the two named indices, or off the sentence-vs-question test, and pin it.
  • Both language banks. Spanish labels are longer; the 42% label column has to hold them without pushing the value column around. Check the PAP consent sentence and PMD index 24 in ES.
  • Email-safe throughout — tables, inline styles, literal hex, no var(), no web fonts, ≤600px. Same constraints the existing template documents.
  • Server esc on every rendered value; PPD's payload.rows render verbatim (INV-89).
Two things the existing design doc is missing
You didn't pick either for this pass, so I've left them out — but docs/…/Email Templates.dc.html is now behind what ships, and someone will eventually build from it. The Send feedback button (added 2026-08-13, its replies render in Sent detail) and the AMENDED / superseded state both exist in the product and appear nowhere in the design. The amended one carries real risk: the code marks it "clearly … to you and the recipient", and a superseded copy that reads as current is a wrong-order path. Worth adding to that doc even if the emails don't change.
